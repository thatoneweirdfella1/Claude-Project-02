## Read this first — the whole method in one minute

The site will not be completed one feature, panel, payment system, or screen at a time. It will be completed in **horizontal passes across the entire product**.

| Pass | Honest result after the pass |
|---|---|
| Layer 1 — Reachable | Every approved part of the site exists in the whole-site map and every navigation control reaches the correct destination. |
| Layer 2 — Interactive | Every visible control responds with the correct immediate state, menu, dialog, selection, validation, or safe refusal. |
| Layer 3 — Locally Useful | Every feature that can work without a real account, payment, or provider performs a genuine end-to-end local/manual job. |
| Layer 4 — Durable | Identity, saved data, recovery, synchronization, and resumable work function across the whole site. |
| Layer 5 — Money-Safe | Every allowance, entitlement, payment, cap, receipt, and potentially paid path is controlled by an authoritative fail-closed system. |
| Layer 6 — Connected | Real provider registries, connections, adapters, translations, AI routes, Multi-AI, and large jobs function through the already-safe foundation. |
| Layer 7 — Web Production-Verified | The supported web product passes matching-deployment, security, recovery, accessibility, ADHD-friction, migration, and failure testing. Desktop remains a separately governed track. |

If usage ends after Layer 2, the correct summary is: **“The entire site is Reachable and Interactive; deeper functionality has not yet been claimed.”** It is not: “the top panel works, payments are half-built, and nobody knows what else is usable.”

The currently requested “make every link go where it belongs across the whole site” work is **Layer 1 work**. This plan does not claim Layer 1 is already complete.

## 1. Purpose

This system exists to produce four outcomes:

1. Every completed pass improves the **entire site** to one known depth.
2. A usage cutoff leaves a coherent last-completed product state.
3. Another account can resume from a bounded layer and exact checkpoint without reconstructing scattered repairs.
4. No visual shell, green build, or placeholder is mislabeled as real functionality.

The 39 v2 repair groups remain the defect/evidence register. They are **not** 39 independent implementation jobs. Work is organized by whole-site depth, shared architecture, and coherent batches. A repair group can be touched in several layers and closes only when its deepest required behavior is proven.

## 2. Non-negotiable authority

Implementation must obey this order:

1. A dated, explicit user correction that names or unambiguously changes the affected scope; it supersedes older authority only inside that scope.
2. Approved/frozen requirements and GREEN decisions.
3. Approved architecture and implementation decisions.
4. Current source code as implementation evidence.
5. Matching deployed behavior as live evidence.
6. Clearly labeled inference only when the above are silent.

Code, an old commit, a test, current live behavior, or timestamp alone cannot create or replace a product decision merely because it exists. Unresolved choices remain unresolved and block only their exact affected behavior. If two controlling-looking sources still conflict after scoped precedence and supersession are applied, record `CONFLICT — UNRESOLVED`; do not choose by recency.

The corrected denominator is the v2 authority: **218 permanent requirement/control IDs**. No layer may define its own smaller universe and then claim 100% coverage of it.

3. Quick Actions, Quick Tools, right rail, customization, recent work, usage, context, and AI status.
4. Sessions, Saved Tools, Templates, Saved Prompts, Projects, Insights, variables, checkpoints, and Personal Optimization.
5. Account, plan, allowance, entitlements, payments, credits, caps, receipts, settings, data export, and cross-device behavior.
6. Provider/model registry, Universal/manual handoff, provider adapters, BYOK, licensed connections, optional companion boundaries, connection removal, Fable-under-Claude, and real execution routes.
7. Large-job orchestration, learning signals, cost-bounded resume, evidence preservation, and final synthesis.

Backend-only requirements do not need invented screens. They must still receive a layer status, evidence target, and an explicit `NOT USER-FACING` designation so they cannot disappear.

## 4. Permanent operating rules

### 4.1 Horizontal completion rule

A layer is not complete because its easiest screens passed. It earns its layer label only after **every one of the 218 IDs** is marked for that layer as either:

- `PROVEN`; or
- `N/A AT THIS DEPTH — <exact matrix reason>` where that exact ID/layer reason is resolved in `LAYER-OBLIGATION-MATRIX.csv` from the versioned `LAYER-OBLIGATION-PROFILES.yml`.

`PASS` and `FAIL` are process-gate results only; they are never coverage-ledger statuses. Any applicable `IMPLEMENTED — NOT FULLY PROVEN`, `PARTIAL`, `NOT STARTED`, `BLOCKED — <reason>`, `CONFLICT — UNRESOLVED`, or `UNKNOWN — INSPECTION REQUIRED` keeps the layer incomplete. A decision, project task, permission, credential, or external blocker must be named exactly; it cannot be converted to `N/A`. Unrelated implementation may continue only when it cannot depend on or silently decide the blocker, and the last stable product-depth claim remains the prior completed layer.

### 4.2 Additive-code rule

Each layer adds permanent capability. Early layers may use test adapters or clearly labeled unavailable states, but they must use the same interfaces intended for the real services. Do not build a fake successful payment, account, provider, or save path that will later be discarded.

### 4.3 No false-success rule

Before a real backend exists, a control may:

- open the correct destination;
- collect and validate inputs;
- demonstrate its approved UI states with a test adapter;
- complete a genuine local/manual workflow; or
- state plainly that a connection is not configured.

It may not pretend that a purchase, provider call, remote save, allowance change, synchronization, or other external effect succeeded.

### 4.4 Safe external-effects rule

No real paid/provider execution is enabled before the Layer 5 money-safety gate passes. Before that gate, external-effect code remains disabled, sandboxed, dry-run, or manual-only. The Layer 5 gate must record its exact commit and matching evidence before Layer 6 work may enable real execution; no invented feature-flag name or unapproved mechanism is required. Universal/manual handoff remains the genuine no-key route.

### 4.5 Shared-system rule

Fix shared routing, state, persistence, service, provider, and billing foundations once, then apply them across every consumer. Do not repeat near-identical logic separately inside screens merely to close repair rows.

### 4.6 Repair-row rule

Repair IDs are coverage obligations, not the work sequence. Do not perform 39 separate inspect-edit-build-deploy cycles. One coherent change may satisfy evidence for several repair IDs, and one repair ID may remain open across several layers.

### 4.7 Stable-checkpoint rule

The last completed layer must always remain identifiable and usable. Every layer gate uses an immutable deployment bound to its exact commit. A stable alias may move only after the gate passes, an independent audit record is valid, the user accepts it, and `promote_stable_preview` is explicitly granted. Partial next-layer work must never replace the stable alias. Rollback moves the alias to the prior immutable deployment; it never rewrites evidence.

### 4.8 Testing-efficiency rule

- Use focused tests during a coherent implementation batch.
- Run one full build/test gate at the end of the batch.
- Run the complete whole-layer suite and independent audit once at layer exit.
- Do not redeploy after every repair-row edit.
- A green build proves compilation/tests only; it does not prove the layer or product works live.
- A test result used for layer promotion must name the acceptance-test handle, the layer, the assertions exercised at that depth, the environment, and the actual result. One undifferentiated full-depth verdict cannot be reused as proof for every layer.

### 4.9 User-decision rule

Ask only genuinely unresolved product decisions. Present one consolidated choice at a time with the recommendation, reason, consequence, and the exact behavior accepted by `GO`. Never make the user inspect repair rows, tests, or implementation alternatives that authority already resolves.

### 4.10 No-scope-drift rule

No redesign, new feature, or “while here” cleanup may enter a layer unless required by an approved ID or necessary to safely implement it. Incidental discoveries go into a separate finding row; they do not silently enlarge the active layer.

### 4.11 Usage-cutoff rule

After the first usage-limit warning or when remaining usage is clearly near exhaustion:

1. Do not start another coherent batch.
2. Finish, disable, or isolate the current batch so the last stable checkpoint is intact.
3. Run the smallest proof needed to describe its actual status.
4. Commit only coherent work.
5. Update the layer ledger and handoff before doing anything else.

There is no invented fixed token or percentage reserve. If coherent work cannot be committed, run `stopping-checkpoint.mjs`: it must mark the state unsafe, capture a hash-bound recovery patch and untracked-file snapshot, and refuse to call the handoff safe until the work is restored, tested, committed, and remote-head verified.

### 4.12 Evidence rule

Every `PROVEN` cell has a matching record in `LAYER-EVIDENCE-INDEX.jsonl` containing its exact resolved obligation code and assertion, commit, matching preview/deployment identity where live behavior is claimed, layer-scoped test/workflow results, hash-bound artifacts, actual result, and a separate accepted independent-audit record. The implementation session cannot certify its own work. Source inspection, unit tests, screenshots, and deployment status are useful evidence but do not individually establish complete end-to-end behavior.

### 4.13 Regression, demotion, and failed-gate rule

If a later change touches implementation or evidence on which a completed layer depended, the affected evidence becomes stale. The working branch may not claim that layer until it is re-proven; the separately recorded last stable layer checkpoint remains the rollback/reference point. A failed layer gate leaves the layer `INCOMPLETE`, records every failing or blocked row and one exact next action, and never promotes a partial layer.

## 5. Layer-status vocabulary

Use these product-depth labels exactly:

| Label | Meaning |
|---|---|
| `L0 COVERAGE LOCKED` | Authority, denominator, scope, and tracking are ready. No product-function claim. |
| `L1 REACHABLE` | Site-wide routes/destinations and frozen shell are proven. No deeper behavior claim. |
| `L2 INTERACTIVE` | Immediate control behavior and UI states are proven. No remote/persistent result claim. |
| `L3 LOCALLY USEFUL` | Genuine local/manual workflows are usable without pretending external effects. |
| `L4 DURABLE` | Approved identity, persistence, recovery, sync, and resumability are proven. |
| `L5 MONEY-SAFE` | Real monetary and allowance effects are authoritative, bounded, idempotent, and fail-closed. |
| `L6 CONNECTED` | Real provider/connection/execution behavior is proven through the safe foundations. |
| `L7 WEB PRODUCTION-VERIFIED` | Complete supported web behavior is proven end to end on the matching deployment; desktop is not claimed. |

Never replace these with the vague words `done`, `finished`, or `working` without naming the depth.

## 6. Required coverage ledger

Before implementation, maintain one canonical RFC 4180 ledger with one row for each of the 218 permanent IDs and these columns:

| Column | Required content |
|---|---|
| `permanent_id` | Existing or v2 permanent requirement/control ID. |
| `authority_citation` | Exact controlling source. |
| `repair_ids` | Every related `V2-RQ-*` ID. |
| `decision_ids` | Exact `V2-DQ-*` IDs or blank. |
| `workflow_ids` | Every related workflow ID. |
| `test_ids` | Permanent-control and workflow acceptance handles. |
| `L1` through `L7` | One exact allowed ledger status, checked against that ID's resolved obligation matrix row. |
| `last_verified_commit` | Full commit for the most recent current proof, or blank. |

Implementation paths, test results, deployment identity, artifacts, actual result, and auditor result belong in `LAYER-EVIDENCE-INDEX.jsonl`, not multiline CSV cells. `CURRENT-LAYER-STATUS.md` and `HANDOFF.md` hold the one bounded next action.

Required reconciliation after every layer:

- 218 authority IDs versus 218 ledger rows;
- every current route/control/API/store action versus a permanent ID or explicit exclusion;
- every `V2-RQ-*` versus at least one ledger row;
- every `PROVEN` cell versus complete layer-appropriate evidence;
- every registered workflow and all 266 acceptance handles versus at least one ledger/evidence mapping;
- every `N/A` versus the exact resolved matrix entry and reason;
- every unresolved item versus an exact blocker or next action; and
- zero unexplained differences.

## 8. Layer 1 — Whole-Site Reachability and Frozen Shell

### Honest outcome: `L1 REACHABLE`

Every user-facing destination required by the v2 permanent-ID registry and Control & Behavior Map exists under the approved name and location. Every global, top-bar, left-nav, Quick Action, Quick Tool, right-rail, screen-level, account, billing, connection, and operator-entry navigation control lands on the exact required destination or opens the exact required container. The destination renders its required shell without a router error, blank screen, or false-success state; gated or unconfigured destinations show an honest labeled state. Obsolete duplicate destinations are unreachable. Frozen geometry and visual identity are preserved.

### This layer does

- establish the single canonical `ScreenId`/route map;
- wire every navigation-producing control to it;
- create every approved screen shell and required subsection anchor;
- remove or retire obsolete Home, Messages, Archive, duplicate Dashboard, alternate-layout, and other unapproved destinations;

- include account, plan, billing, provider, connection, large-job, learning, and Developer surfaces in the route inventory even though their backends are later layers;
- preserve capped/frozen desktop geometry and both approved appearance modes; and
- protect normal typing from approved shortcuts while leaving undecided browser-reserved shortcuts unresolved.

### This layer does not do

It does not claim that controls inside the destination perform their job, data persists, accounts exist, payments occur, or AI providers run.

### Exit gate

1. Every approved navigation source is enumerated and tested.
2. Every destination is exact; no control lands on a semantically similar but wrong screen.
3. Back/return behavior preserves the current draft and location where already required by the shell contract.
4. No obsolete duplicate route remains reachable.
5. Light/dark shell screenshots match the frozen visual authority at the approved desktop canvas.
6. Every non-navigational control is visibly classified for Layer 2 rather than silently assumed functional.
7. Any live `PROVEN` claim names a working preview and its deployment identity matches the tested commit. Missing deployment permission or identity blocks promotion, not unrelated source work.

### User’s simple check

## 18. Execution workflow used inside every layer

Each layer follows the same bounded operating cycle:

1. **Resume:** Read the governing instructions, current layer status, exact checkpoint, and active blockers before inspecting code.
2. **Preflight:** Run `node scripts/governance/preflight.mjs --action=modify_application_behavior`; a `FAIL` is a stop condition, not advice.
3. **Snapshot:** Record branch, exact local and remote lease commits, preview, test counts, dirty files, and last completed layer.
4. **Select coverage:** Resolve the exact permanent IDs, obligation codes/assertions, allowed paths, and tests in `BATCH-SCOPE.json`.
5. **Group shared work:** Batch by shared router, state machine, service, store, or adapter—not by repair-row number or screen.
6. **Implement one coherent batch:** Preserve all prior layer contracts and keep later external effects disabled.
7. **Focused proof:** Run affected tests and inspect the actual rendered/behavioral result where appropriate.
8. **Checkpoint:** Commit coherent work and update the ledger; do not label the layer complete.
9. **Repeat:** Continue the next site-wide batch until every applicable ledger row is resolved.
10. **Whole-layer gate:** Run full tests/build, immutable matching preview, whole-layer acceptance suite, coverage reconciliation, and one independent read-only audit whose session differs from implementation.
11. **Promote the checkpoint:** After the audit passes, the user accepts it, and the promotion permission is granted, record the exact layer-complete commit/preview and only then begin the next layer.

If step 9 fails, do not promote. Record the failing IDs/tests/evidence, preserve the last stable layer checkpoint, define one bounded corrective batch, and rerun the gate only after the recorded failures are addressed.

The active task name should always be the layer, for example `complete-layer-2-interaction`, never a growing list of unrelated repair tasks.
